# Database design

MongoDB Community Edition is the primary store. TypeORM Mongo repositories handle ordinary entities; the native driver handles capabilities TypeORM does not expose. Both use one configured URI and database name. **The database name must appear in the URI path as well as TypeORM's `database` option**: the Phase 0 probe found that an empty URI path can make TypeORM use a default database.

A native transaction uses one `MongoClient` and one session for every write. A session cannot be passed to TypeORM's separate internal client. Repository interfaces must keep this distinction explicit. TypeORM remains the primary persistence abstraction for nontransactional CRUD.

Planned collections: `users`, `roles`, `customers`, `carriers`, `carrier_accounts`, `phone_numbers`, `number_holdings`, `number_assignments`, `number_events`, `purchase_orders`, `port_requests`, `port_request_numbers`, `background_jobs`, `job_events`, `carrier_sync_runs`, `reconciliation_issues`, `operation_outbox`, and `security_audit_events`. GridFS uses its files/chunks collections.

Phase 2 registers TypeORM Mongo repositories for all 18 core collections and creates their indexes through versioned, rerunnable initialization. `schema_migrations` stores the applied `core-v1` marker. Database readiness initializes the schema before returning success; operators can also run `pnpm --filter @dataphone/api db:init` after building the API. `db:seed` idempotently creates the four initial role names. Phase 3 defines their permissions and user management.

Unique indexes enforce normalized user email, role key, customer external ID, carrier code, carrier account identity, E.164 number, carrier account/native number identity, one active assignment per number, purchase and job idempotency, port request reference and number identity, and outbox idempotency. Status/time indexes support inventory, job claims, port workflows, reconciliation, and event history. Phone numbers must pass `normalizeE164` before persistence. Future writers must enforce this at the service boundary.

`DatabaseInfrastructure.repository()` is the TypeORM path for ordinary CRUD. `withTransaction()` passes the native `Db` and one `ClientSession` to every write in a multi-document mutation. TypeORM's separate client must not be called inside that callback. `updateWithVersion()` uses an atomic compare-and-swap and rejects stale versions. The helper rejects updates to append-only event collections. GridFS is exposed through the native driver. These helpers do not replace endpoint authorization; later phases must restrict caller permissions.

Historical events are append-only through the application. Hash chains require independently retained checkpoints to detect tampering by a highly privileged database operator. Backups and restore drills are required before production use. A single-node replica set supports transactions and Change Streams for this POC but has no failover.

Phase 7 stores customer and ownership changes in `number_events` with a unique global sequence. The `audit_chain_heads/global` document serializes writes in the same transaction as business state and records the latest SHA-256 hash. Each event includes actor, related customer/number, previous and new values, timestamp, and previous hash. The application verifies the chain but has no external checkpoint yet. One active assignment per number is enforced by the partial unique index; closed assignment records preserve ownership periods.
